# DESIGN — трекінг зупинок і маршруту

**Статус:** проєкт рішення, не реалізовано. Дата: 2026-10-17.

## 1. Що хочемо отримати

1. Під час відкритої зміни телефон у фоні веде трек.
2. Виявили стоянку → сповіщення «Це пауза?» + запит одометра (координати вже є, їх питати не треба).
3. Почався рух автомобіля → запис «Продовження руху», пауза закривається.
4. Маршрут авто — суцільна лінія, переміщення пішки під час паузи — пунктир.

## 2. Модель даних (пропозиція)

`records` лишається подіями, як зараз. Додаємо:

```sql
CREATE TABLE track_segments (
  id INTEGER PRIMARY KEY,
  trip_id INTEGER REFERENCES trips(id) ON DELETE CASCADE,
  device_id INTEGER REFERENCES devices(id),
  mode TEXT NOT NULL,            -- 'drive' | 'walk' | 'still' | 'nosignal'
  started_at INTEGER NOT NULL,   -- unix ms
  ended_at INTEGER NOT NULL,
  distance_m INTEGER,
  polyline TEXT,                 -- encoded polyline (Google-алгоритм)
  pause_record_id INTEGER REFERENCES records(id) ON DELETE SET NULL
);
```

Один сегмент = один безперервний відрізок одного режиму. 10 годин зміни → ~15–25 сегментів
по 2–20 КБ, а не 1200 окремих точок. Точки зберігаємо тільки всередині polyline.

Зв'язок: `pause_record_id` у сегменті `walk` вказує, до якої паузи належить ходьба.

## 3. Стан-машина на телефоні

```
IDLE ──(рух > 15 км/год 60 с)──▶ DRIVING
DRIVING ──(зміщення < 50 м за 3 хв)──▶ STOPPING
STOPPING ──(3 хв підтверджено)──▶ PAUSED  (+ сповіщення «Пауза?»)
PAUSED ──(швидкість > 15 км/год 60 с)──▶ RESUMING ──▶ DRIVING
будь-який ──(немає GPS > 2 хв)──▶ NOSIGNAL ──▶ повернення в попередній
```

Ключове: **поки стан PAUSED, будь-яке переміщення — пішки**. Це знімає проблему
«як відрізнити пішки від авто на 5–8 км/год»: у стані паузи авто стоїть за визначенням,
отже рух — це водій з телефоном. Відновлення руху вимагає > 15 км/год протягом 60 с —
пішки стільки не ходять, а авто в заторі повзе 5–10 і поріг не перетне.

## 4. Недоліки запропонованої логіки та рішення

| # | Недолік | Наслідок | Рішення |
|---|---------|----------|---------|
| 1 | Швидкість ≈ 0 як ознака зупинки | GPS «дрижить» на 10–30 м, дає фальшиві 2–5 км/год — зупинка не фіксується | Рахувати **зміщення за вікно** (радіус < 50 м за 3 хв), а не миттєву швидкість |
| 2 | Світлофори, затори, черги на складі | 10–20 сповіщень за зміну → водій вимикає функцію | Поріг 3 хв (не 2), не частіше ніж раз на 30 хв, ігнорувати точки біля попередньої паузи (< 200 м) |
| 3 | Втрата GPS у тунелі, складі, підземному паркінгу | Система вважає це стоянкою або стрибком маршруту | Окремий стан `NOSIGNAL`; розрив у треку не закриває паузу і не малює пряму лінію через тунель |
| 4 | Android вбиває фоновий сервіс (Doze, Xiaomi/Samsung) | Трек тихо зникає, водій не знає | Foreground service типу `location`, запит на exemption від battery optimization, watchdog + індикатор «останній сигнал 12 хв тому» у PWA |
| 5 | «Авто чи пішки» за швидкістю | Зона 5–8 км/год спільна для затору й швидкої ходьби — неминучі помилки | Не класифікувати за швидкістю; правило стану PAUSED (розділ 3) + поріг відновлення 15 км/год |
| 6 | Телефон лишився в кабіні | Пішохідний трек неможливий — водій ходив без телефона | Не вдавати, що знаємо: показувати «пристрій не рухався» і малювати пунктир лише там, де є дані |
| 7 | Запит одометра в момент зупинки | Водій паркується/маневрує, цифри перед очима немає — введе навмання | Питати **при відновленні руху** (водій уже в кабіні); префіл = останній одометр + пробіг по GPS, з можливістю виправити пізніше |
| 8 | Одометр менший за попередній | Типова помилка вводу, ламає пробіг зміни | Валідація на клієнті й сервері: попередження + вимога підтвердити |
| 9 | Два телефони ведуть трек | Дві паузи, два треки, подвійні сповіщення | Один активний трекер (прапорець на `devices`) + серверна дедуплікація пауз ±5 хв / 200 м |
| 10 | Водій не відповів на сповіщення | Пауза губиться або висить вічно | Таймаут 10 хв → автозапис паузи з `source='auto'`; водій може скасувати або виправити |
| 11 | Рух не відновився (зміну закрили) | Пауза без кінця | Закриття зміни/рейсу примусово закриває відкриту паузу |
| 12 | Застосунок убито під час паузи | Стан-машина в пам'яті втрачена | Стан відновлюється з БД: останній запис + відкрита пауза |
| 13 | Обсяг даних | 1200 точок/день → БД росте на сотні МБ/рік | Сегменти з polyline + спрощення Дугласа–Пекера (10 м); ~300 КБ/день |
| 14 | Офлайн у рейсі | 1200 POST-запитів або втрата треку | Батчі по 5–10 сегментів, локальна черга в APK, відправка при появі мережі |
| 15 | Батарея | Безперервний high-accuracy GPS — 15–20 %/год | `balanced` у русі (30 с), `high` при зупинці, пауза трекінгу при закритій зміні |
| 16 | **Карта** | У CSP немає зовнішніх джерел — базової карти немає | Три варіанти, див. розділ 5 |
| 17 | Звіт стане шумним | 20 пауз = 40 рядків у зміні | Згортати «Пауза → Продовження руху» в один рядок з діапазоном і тривалістю |
| 18 | Пробіг по GPS ≠ пробіг по одометру (1–3 %) | Розбіжність у звіті | Показувати обидва, не змішувати; зарплатня рахується по одометру |
| 19 | Трек = повний журнал переміщень, зберігається вічно | Конфіденційність | Прийнято власником (DECISIONS 2026-10-17), але варто знати масштаб |

## 5. Карта — головне невирішене питання

| Варіант | Що бачить водій | Ціна | Обмеження |
|---------|-----------------|------|-----------|
| A. Без базової карти (canvas/SVG) | Лінію на сітці з масштабом | ~2 год | Вулиць не видно, лише форма маршруту |
| B. Leaflet + тайли OSM | Звичну карту | ~4 год | Зовнішні запити → послабити CSP (`img-src`), політика OSM обмежує навантаження |
| C. PMTiles локально | Карту регіону, працює офлайн | ~1 день | 200–500 МБ на регіон у репозиторії/образі |

Рекомендація: **B** для старту (дивитись маршрут будуть удома, не в полі), **C** — якщо
знадобиться офлайн або вимога «жодних зовнішніх запитів» стане жорсткою.

## 6. Фази

1. **Трекер + пауза/продовження** (backend + APK), без карти. 2–3 дні.
2. **Сегменти маршруту + карта** (лінія/пунктир). 2 дні.
3. **Аналітика**: час у русі/на паузі, пробіг по GPS, порівняння з одометром. 1 день.
